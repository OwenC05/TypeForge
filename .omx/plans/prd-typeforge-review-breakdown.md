## 2. RALPLAN-DR

### Principles

1. **Practice value first:** optimize entering, continuing and understanding practice before showcasing ML.
2. **Separate claims:** working controls, a responsive policy, useful recommendations and retained typing improvement require different evidence.
3. **Preserve valid evidence:** never rewrite old results/predictions or silently mix assessment cohorts to make progress look better.
4. **Keep the working core:** preserve native editing, local-first privacy and existing utilities; choose the smallest reversible change.
5. **Personalize honestly:** a meaningful general fallback is better than a weakly supported “weakness”; every suggested focus needs provenance and a limitation.

### Top three decision drivers

1. Immediate improvement of usability and UI craft in the repeat daily journey, with adoption treated as a hypothesis to evaluate rather than a promised percentage.
2. A real feedback path from practice to the next useful activity, without compromising measurement.
3. Cost and regression risk relative to what the evidence can currently justify.

### Viable alternatives

| Option | What it delivers | Advantages | Costs/limits | Disposition |
|---|---|---|---|---|
| A. Coherent General/manual practice foundation | Claude-reviewed ready/running layout, in-place result, remembered settings, repeat and practice summary; compare refined-current and practice-stage prototypes | Directly addresses observed adoption friction; useful without personalization; preserves simple choice | Does not yet adapt automatically to practice evidence; perceived and actual user preference need checking | Viable standalone release and first increment |

### Corrections and limits that change the plan

- **Practice is already in saved history.** `app.ts:683-695` renders both modes. P4 adds a practice activity/goal summary; it does not “fix missing practice storage” or mix practice WPM into the assessment trend.
- **The common-pair dose reversal is real under the stated analytic comparison.** L reports `th` at about 3.151 versus 2.373 occurrences/100 characters and `he` at 3.268 versus 2.408 for general versus the current full-cycle targeted schedule. These are expected corpus exposures, not time-based dose in a short run, human recommendation yield or learning effects.
- **Corrected errors are not lost from all metrics.** Attempt accuracy and expected-key error counts retain them; the clean timing sample excludes the edited sentence. P5 needs a separate coaching observation contract, not relaxed benchmark filtering.
- **A stable target overlay is prototype-only.** Even identical word-wrap CSS can diverge because the textarea contains the response while the mirror also includes the untyped suffix. Use the clarified first-mismatch marker and conditional caret pointer without altering text flow; do not infer edit-distance alignment or invented “inserted” errors from positional scoring.
- **No global printable-key capture at all.** Contextual autofocus and a real focus-recovery control replace that withdrawn proposal. A body-only, unmodified, noncomposing Enter may activate the input; typing in controls never does.
- **Layout must not select content.** At a fixed seed/mode/settings/lineage, viewport changes cannot filter, reorder, shorten, substitute or reweight prompts or change result settings. Width-dependent content is a separate versioned practice-only proposal, outside the baseline; no assessment-bank change is hidden in a wrapping fix.
- **The ML numerical defect is not a scientific threshold decision.** Uniform histories must abstain across summation orders. Numerical tolerance cannot substitute for a meaningful effect/support/stability policy; that policy is defined explicitly in Stage 2A.
- **Pause is not included in the first fix.** Initially show focus loss immediately and preserve current timed-run interruption semantics. A later practice-only pause would need a versioned clock/scoring contract; assessment validity must not silently change.
- Monkeytype's observed first key focused the input but was absorbed. The comparison supports improving entry/focus, not claiming every competitor first key was scored or that its untested accessibility/editing paths are inferior.

### Stage 1D — Separate native Undo/Redo contract and versioned repair (E2)

This is not a CSS/UX cleanup. Stage 1 may ship an accurate persistent Undo notice while this bounded task is reviewed. **Resources:** `app.ts:127-148,362-383`, `engine.ts:205-214,260-381,453-466`, `profile.ts` compatibility, `storage.ts` validation and native browser tests.

**Selected proposed semantics:**

1. Recognize `historyUndo`/`historyRedo` only when the browser's before/after value matches a uniquely justified replay of the bounded accepted-edit journal **within the current passage**. Test browser-coalesced edits, selection replacement and word deletion; never infer history solely from an arbitrary longest-common-prefix text diff. Ambiguous, unsupported or cross-commit replay retains conservative unsupported-input handling and explicit notice. Committed passages cannot be changed; restore the retained active value if a native event attempts to cross that boundary.
2. Replay changes retained response text/selection and therefore positional correct-character WPM, but does **not** add new insertion attempts, first attempts/errors or press timings. Original accepted insertion/error counters are monotonic; undo does not erase earlier mistakes, and redo does not count them twice. Subsequent genuine typing counts normally. `deletedCharacters` counts characters actually removed by edits, including supported replay removals; label that definition. No claim is made about physical-key confusion or edit-distance alignment. **Pre-admission deletion guard:** preserve the existing `MAX_ATTEMPTS = 16,384` bound on `deletedCharacters` for v2 as well as unchanged v1 validation. Before any candidate replay or ordinary edit mutates accepted state, compute its actual removal count from the uniquely justified transaction. Accept only if accumulated deletions plus that count is at most 16,384, together with the existing other bounds. This applies across prior passage/deletion history, coalesced replay, replacements and ordinary deletion after restored text, not merely to replay-operation count. If it would exceed the bound, reject the entire edit atomically: cancel beforeinput when possible, otherwise restore the last accepted textarea value and pre-edit selection; preserve accepted counters, journal and prediction/timing evidence unchanged. Show a truthful bounded notice that this edit was not applied because the deletion limit was reached. The timer/session continues under existing rules; other admissible edits, normal completion and explicit restart remain available. A later native-history transition that no longer uniquely matches the accepted journal uses the existing unsupported-history path. Do not clamp counts, silently drop accepted removals, partially accept the edit, invent timestamps or postpone rejection until saving. This rejection alone does not invalidate already accepted accuracy.
3. Any supported history replay marks that sentence edited and excludes all its clean timing/prediction-match observations; prior frozen predictions are never rewritten and no restored glyph receives a fabricated timestamp. Valid attempt accuracy remains available for the run, and supported history correction alone does not flag the whole run. Existing interruption/composition/unsupported-input rules still apply. The journal is bounded by existing response/attempt envelopes plus an explicit replay-operation cap; overflow becomes a visible unsupported-history state, not unbounded memory or invented accounting.
4.
