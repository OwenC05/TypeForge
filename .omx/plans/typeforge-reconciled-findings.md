## Reconciled competitor and design conclusions

Actual Claude's K1-K12 live Keybr review covers tour, focus/error behavior, four synthetic lessons with visible letter unlock, profile/settings, return and simulated mobile. Monkeytype guest coverage is from the first design round. Neither establishes learning efficacy, human preference or universal accessibility.

- **Monkeytype reference:** immediacy, quiet running state and easy repeat. The observed first key focused and was absorbed, not scored.
- **Keybr reference:** visible changing practice state, in-place lesson continuation and an understandable path. Its observed narrow-screen clipping and captured Tab behavior are not patterns to copy. Its adaptive-learning claims remain unmeasured marketing here.
- **TypeForge opportunity:** calm, local, private-by-default practice with a strong native editing core; improve entry, hierarchy, continuity and useful feedback. This is Claude's design hypothesis, not measured competitive superiority.
- **UI scope:** coherent redesign of practice, in-place results, returning Home and practice summary is justified for a prototype comparison. A wholesale identity/theme replacement currently has no supporting evidence; colour roles and visual hierarchy can change.
- **Interaction resolution:** no global printable-key capture; intentional-entry focus only when controls/AT are not displaced; explicit focus recovery. Stable-target custom rendering is prototype-only. Default correction cues preserve native text geometry. Layout cannot change prompt IDs/order by viewport.
- **Essential state:** compact chrome must preserve visible integrity/Undo notices, an accessible focus control and truthful block identity in a stable feedback area. Why/details controls must not appear active while silently ignoring activation.

## Cross-cutting evidence limits

- Real screen-reader speech, forced-colors behavior, OS IME, physical devices, Firefox/Safari and actual browser zoom remain unverified. Distinguish observed semantics from claimed universal accessibility. D F10's over-announcement is a hypothesis, not a reproduced AT defect.
- Three source-sliced tests failing does not negate the independently passing build/browser results; those passes also do not make the whole check green.
- A stricter clean-timing sample is appropriate for its stated measurement task; it becomes a product problem when treated as a complete diagnosis. Preserve the task and add a separate coaching contract.
- Existing strengths include native selection/editing, local saving/export/deletion, bounded engine/caps, honest experimental labels and recoverable transient save failures. Improvements must retain these.
- No study recruitment, data upload, broad model rewrite, production deployment or application changes have occurred. UI/flow redesign remains an option after Claude's comparative critique; no framework/backend rewrite is implied by changing the experience.
