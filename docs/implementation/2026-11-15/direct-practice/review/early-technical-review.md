## Confirmed findings

### ET-1 — HIGH: Again/settings can discard the only recovery path for an unsaved result

**Location:** `typing-app/client/src/app.ts:431` (Again always requests restart), `:659–660` (result-state settings also request restart), `:666` (generation advances), `:711–712` (completion and its action closures removed); save continuation guards at `:471` and `:477`.

**Trigger:** Complete a practice block with unavailable storage, then activate Again before exporting/retrying. The same loss is possible by changing a result-state setting, or activating Again while persistence is pending and the save subsequently fails. These are available actions; the disabled hidden Restart button does not prevent its handler being called directly by Again/settings.

**Observed evidence:** [probe.mjs](early-technical-evidence/probe.mjs) evaluates the actual frozen `finish`, `afterResultRendered` and restart bodies with a delayed/rejected save and a small DOM-removal fake. In both the already-failed and still-pending cases, Again advances generation, replaces the engine and clears completion; the old Export and Retry buttons disappear. On pending failure, the old catch returns at the generation check without presenting recovery. The recorded output is [probe.txt](early-technical-evidence/probe.txt). This is source execution with host fakes, not a browser reproduction.

**Consequence:** Source-confirmed removal of the only app UI references to that completed payload. If it was not persisted/exported, the user cannot recover it through the result UI after continuing; pending-save failure is silently superseded. Browser manifestation is inferred from these actual handlers and DOM removal semantics. Generation guards correctly prevent stale writes, but do not preserve unsaved data.

**Bounded fix:** Keep an unsaved completed payload and its export/retry UI reachable across continuation, or prevent Again/result-setting continuation from disposing it until save/export or an explicit discard decision. Apply the same policy to both entry points; preserve single-flight saving, permanent-validation behavior and stale-generation protection. Add regressions for failure-before-Again, delayed failure after Again, and settings-driven continuation. Do not weaken the existing save guards to fix this.

### ET-2 — MEDIUM: optional calibration attempts to freeze first-sentence predictions twice

**Location:** `typing-app/client/src/app.ts:728` (initial `prepare`), `:255–258` (unconditional prediction attachment), `:743` (idle/empty is treated as untouched), `:752–754` (second `prepare`); engine rejection at `typing-app/client/src/engine.ts:188`.

**Trigger:** Open QWERTY practice/assessment with the bundled valid artifact, leave the first sentence idle, and let optional history calibration resolve. This includes a remembered QWERTY visit or `/?qwerty=1` with no history. Initial `prepare()` already has finite artifact-backed predictions and freezes them. The callback later sees idle/empty and calls `prepare()` again on the same engine/sentence.

**Observed evidence:** The probe uses the actual frozen app preparation/calibration callback source, actual `TypingEngine`, `predictSentence`, `buildHistory` and committed model artifact. Both idle and no-op-edit variants reject with `RangeError: Predictions must be exhaustive, finite and frozen once before editing the current sentence.` A single accepted insertion switches to running and avoids this second attachment. The production `void calibration(...).then(...)` has no rejection handler. See [probe source](early-technical-evidence/probe.mjs) and [output](early-technical-evidence/probe.txt).

**Consequence:** Source-confirmed exception in the optional callback on an ordinary idle QWERTY entry. An unhandled promise rejection in the browser is inferred; this pass did not execute one. Engine guards retain the original frozen predictions, so this is **not** evidence of prediction overwrite, double-counted typing or corrupted scoring. Optional enrichment fails partway through UI preparation. Idle/empty is also insufficient to distinguish a no-op edit: the engine records every edit attempt as `sentenceEdited`, correctly refusing later attachment.

**Bounded fix:** Track sentence preparation/edit state explicitly and attach predictions at most once, before any edit attempt. Retain already-frozen predictions for the current sentence and apply arriving history to later eligible preparation; separate informational refresh from prediction installation. Handle optional callback rejection without blocking General practice. Add regressions for idle QWERTY with empty/warm history, no-op edit while history is pending, and accepted input/passage advancement before history resolves. Keep the engine's freeze guard intact.
