## S1 — Medium: pure legacy admission lacks its required metadata input

**Evidence:** `interfaces-r2.ts:17–38,130–136`; `lifecycle-r2.md:9`; `implementation-dag-r2.md:10–11,18`. `Authority` supplies database/context/active epoch/revision. `SourceRead` supplies partition/source/ref/membership. `ProjectionInput` supplies those values but neither `legacyEpochId` nor `legacyCutoffCompletedAt` nor an authority-bound legacy-origin admission attestation. D owns pure projection and strict semantics; the read seam does not declare that legacy source admission has already been attested by C.

**Counterexample:** use the author's actual valid lagged assessment source with `completedAt=2026-11-16T11:00:00.000Z` and physical legacy origin. Three strict metadata values can share the exact same `Authority` and `SourceRead`: (a) initial epoch, cutoff12:00; (b) active epoch remains the visible epoch but the legacy epoch is a different old epoch; (c) initial epoch, cutoff10:00. Their required origin decisions are **true/false/false**, while the declared pure input is identical. A deterministic pure implementation cannot recover the omitted fields. It must invent an input, accept stale legacy evidence, or move an undeclared attestation responsibility across leases.

**Minimum correction:** add `metadata: Metadata` to `ProjectionInput`. Pass the already validated metadata read charged in this preparation; do not introduce another scan/store/read. Require semantic agreement of metadata database/default context/active epoch/revision with `authority` and final proof, and apply the physical partition + initial legacy epoch + cutoff rule in D's classification. An alternative is an explicit authority-bound origin attestation on each `SourceRead`, but that would transfer classification into C; the single metadata input is smaller and preserves the present lease split.

This is a missing information seam, not a claim that a production selector already misclassifies data. Current sources still require exact membership/hash/kind/database/context/epoch; passing metadata must not reintroduce timestamp fallback for current rows.

## S2 — Medium: proof-bearing pure output has no actual final-proof input

**Evidence:** `interfaces-r2.ts:58–60,72–84,97–109,130–144,182–188`; `lifecycle-r2.md:50–54`; `implementation-dag-r2.md:10–11,18`. `derivePolicy(ProjectionInput)` returns a `PreparedStatus` and candidate `PracticeSnapshot`. Exact participation/available summary/complete-insufficient coach already require `VerifiedProof`; the candidate snapshot also requires it. Yet `ProjectionInput` contains range authority/scalars but no actual final storage proof. Storage is explicitly responsible for the final transaction **after computation**. `AdmissionInput` later receives a proof, but cannot supply a missing proof for the earlier pure component outputs.

The same range/source/scalar input can exist before a final transaction, after an unchanged successful transaction, or after proof failure. Matching authority numbers do not choose among those states or establish the proof method/admission point. A placeholder `VerifiedProof`, minted `admittedAt`, or shape-only scalar relation is not that actual storage proof. The author tests correctly identify themselves as relations; none implements the missing call sequence.

**Minimum coherent correction:** add `finalProof: VerifiedProof | null` to `ProjectionInput`, alongside S1's metadata. Freeze the following call order in lifecycle/D0: C gathers and validates the bounded range/source/membership data and computes required asynchronous hashes; C obtains its actual final barrier/fallback proof within that same ledger; then D derives proof-bearing components/candidate **using that proof**, or emits truthful pending/unavailable components when it is null. Any pre-proof arithmetic is provisional and must not be published as a proved component. Validate exact method/authority/config/source-selection bindings; never fill the new field by copying matching input scalars. Final local generation/config/epoch/database/pre-insertion checks still precede publication/admission, and `admitPractice` receives the same actual proof.

This option keeps the existing output types and implementation leases. It needs two input fields total with S1, plus an explicit ordering correction to the current "after computation" wording. Alternatively separate provisional projections/candidates from proof-bearing admitted outputs, but that requires more type churn. No extra transaction/budget or persistent proof history is required. This correction does not turn TypeScript into runtime evidence; C must actually produce the proof and semantic validation must check bindings.

## S3 — High: revision exhaustion needs a persistent non-admitting rule

**Evidence:** `lifecycle-r2.md:9,13,15,17,50`; `metadata-membership.schema.json:$defs.metadata.properties.sourceRevision`; `r2-check.mjs:156–165`. Structural metadata allows `sourceRevision=Number.MAX_SAFE_INTEGER`. Ordinary save/export is explicitly retained at exhaustion and counter wrapping/reset is forbidden. The document says optional authority is disabled but specifies no durable field/state transition that makes this observable. The author's actual `revisionProof` relation accepts an unchanged maximum revision when its writer set is complete.

**Counterexample:** a preparation holds valid-looking metadata at MAX; an ordinary current source is saved, or an existing source is deleted; the revision cannot increment and remains MAX; a final transaction sees identical lineage/epoch/revision. Scalar equality and a complete writer inventory still accept the author's relation, while the ordered range/source set changed. The intended sentence "disables optional authority" must be enforceable across reload and tabs, not just an in-memory flag. This is a contract underspecification demonstrated by the relation, not an executed IndexedDB race.

**Smallest amendment using existing fields:** reserve **MAX_SAFE_INTEGER as a terminal, non-admitting revision sentinel**. Structural metadata may retain that integer; semantic authority/capture/preparation/final-admission checks must require `0 <= revision < MAX_SAFE_INTEGER`. Define these transitions explicitly:

- A successful mutation at MAX-1 commits its source/membership/delete/reset changes and revision MAX atomically. This transition immediately disables new optional authority and invalidates any pending MAX-1 preparation; it does not wait for another increment attempt.
- At MAX, ordinary source save/delete/recovery/export may continue under the ordinary source boundary while metadata remains MAX. None creates policy authority or moves back to a lower revision; capture and new preparation are unavailable. Reset cannot claim a new valid baseline epoch at exhaustion.
- Final proof rejects MAX on either side even when the scalar and lineage match. Reload and every other tab read the same persistent sentinel; no transient memory flag or extra schema field is needed. Broadcast invalidates idle state, but the durable sentinel is the proof.
- No wrap, auto-reset, automatic metadata repair, new database name or silent lineage recreation is permitted. Recovery remains separately reviewed; an explicit destructive database recreation, outside this pilot, gets a fresh database identity and invalidates old captures.

This costs no extra infrastructure. Adding a separate durable availability state could also work, but would change schema/types/write paths without being necessary. The sentinel cases in our probes include MAX-1 unchanged, transition to MAX, ordinary write/delete at MAX, reload and cross-tab final rejection. Those are acceptance requirements for the amended protocol, not behavior silently accepted into the frozen author revision.

## Lifecycle, budget and fallback direction accepted in principle

Beyond S1–S3, no further contract-blocking architecture decision was found in the bounded review:

- Atomic v3 upgrade preserves original payloads/index; no bulk scan/migration/copy. Only the upgrade creates authority. Delayed old-time saves go current; deleting a current membership cannot make it legacy. Exact retries preserve original capture; source-saved/membership-unready remains distinct and is not silently repaired. Same ID/different bytes never overwrites; a duplicate across partitions is integrity failure. Old captured epochs stay old across reset. Actual DB recreation changes lineage.
- The writer inventory in `lifecycle-r2.md:21–34` names the existing normal save/retry/delete paths and the new finite/reset/membership paths without pretending future import/admin tools already exist. Version fencing excludes old explicit-v2 opens after upgrade. Out-of-band writes are explicitly outside the revision proof. Missing/corrupt metadata remains unavailable and ordinary recovery cannot bootstrap it again. Real fault/concurrency tests remain required.
- One lookup ledger accounts for both source streams, metadata, memberships, failed/missing points, materialized lookahead and final proof. Reservations differ from charged prefix work; companions/final proof are reserved before sources exhaust capacity. Key-only and count requests have explicit separate finite counts. The storage adapter may use smaller source batches and reuse already validated same-preparation values under coherent authority; it cannot claim repeated actual reads are free. Cooperative slice boundaries yield/join while the same lookup keeps its remaining global allowance. No automatic fresh-cap retries.
- Accepted P3 `HistoryRead.reason` includes `record-limit`, nullable exact oversized total and byte lower bounds; its accepted `scanHistory` propagates the terminal reason. R2 requires every new own partition/companion loop to propagate it too. This needs new consumer tests, not a repeat of H3's primitive audit. Native clone/materialization cost remains distinct from bounded prefix processing. Record-limit never authorizes continuing the other stream or doing unreserved final work.
- Fully fenced writers may use one overlapping final readonly metadata/revision barrier after the relevant reads/hashes. Without that fence, coherent revalidation must cover the ordered range **and** all selected source/membership values within the same allowance; witness-only checks miss inserts. Async hashing stays outside live transactions, with synchronous canonical-data comparison under the coherent fallback. If the complete fallback cannot fit/be expressed, abstention is allowed and fully specified. There is no requirement to invent a complex fallback implementation merely to avoid honest unavailable status.
- Merged cursors preserve both native raw keys, exhausted flags and database identity; no JSON/locale conversion or epoch-based raw-index stop. C owns the adapter rather than claiming the old one-store API alone implements it. Old timed APIs retain their return types/logical source union; finite sources use the separate strict union, new read/history/mixed-export seams and E's validator. Corrupt sources stay stored. Export is explicit, not another automatic policy budget.
