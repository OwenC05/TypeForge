## Ranked blockers and concrete amendments

### R1 — High: a completion-time cutoff cannot establish legacy provenance

**Evidence:** `spec:61,65,67,165,171,175`; P3 `storage.ts:223,274–276,346–347`. Bootstrap currently has no implemented atomic boundary or writer fence. `completedAt` is result completion, not durable insertion time. A pre-bootstrap completed but unsaved result can be saved later; a clock rollback can also give a new result an old completion timestamp. Both satisfy `completedAt <= legacyCutoffCompletedAt` while lacking captured membership. Even after all new writes are atomic, deleting/corrupting a new membership makes timestamp fallback indistinguishable from real legacy evidence.

**Counterexamples:** `probes.mjs` reproduces delayed-save and clock-rollback/membership-loss relations. These are deterministic provenance counterexamples, not observed browser races. A missing post-bootstrap metadata record must remain unavailable; recreating a default context would erase the only reset boundary.

**Amendment:** make physical pre-bootstrap origin explicit. In a single same-database upgrade, retain existing `typeforge/results` as the **legacy partition**, create a **currentResults** store for every later source save, and create metadata/membership stores. Legacy admission requires physical legacy origin, the initial epoch, cutoff and normal exact compatibility. Missing membership in the current partition is always unknown/excluded; completion time never grants it legacy status. No source payload is copied or rewritten. Fence old writers through the database version boundary. See the complete protocol below, including collision/merge/export consequences.

This adds one source store and a two-way storage adapter. The smallest viable single-store alternative is an authoritative bootstrap manifest for every preexisting ID, established atomically with the writer fence. A timestamp-only manifest is insufficient, while eagerly enumerating every source violates bounded automatic bootstrap for large histories. An explicit bounded legacy migration can stage such a manifest, but needs durable proof of which unprocessed IDs were already present. Physical separation provides that proof without a bulk scan, raw-text duplication or a second authority registry. It is my recommended tradeoff, pending root acceptance.

### R2 — High: shared work accounting and final admission still lack one realizable protocol

**Evidence:** `spec:163–171`; P3 `storage.ts:356–385,388–397,412–421,443–465,503–532`; r1 `revision-check.mjs:381–402`. `readHistorySlice.compatible` is synchronous and cannot itself perform an asynchronous membership join. Neither P3's returned valid rows nor its independent 500-row scan cap accounts for membership reads, witness lookups, metadata, sidecar validation or final range/source rechecks. The r1 relation receives already chosen scalar totals; it does not charge actual operations.

500 source reads plus 500 memberships exceed 500. Ten near-1-MiB witnesses read twice exceed 16 MiB before sidecars. A disjoint 20-source coach set and ten-witness milestone set require 30 source reads plus memberships/metadata, already exceeding a single 25-row slice. These examples do not mean the query must fail for typical small records; they mean it must reserve all work and abstain when the proof cannot fit. Do not hide a separate final proof budget or an extra automatic retry.

**Amendment:** one preparation-owned ledger charges every attempted/materialized source, membership, metadata, sidecar and final reread across both partitions; failed/missing point lookups consume an operation/row slot too. Define row accounting and actual byte accounting separately from worst-case reservations and unavoidable single-record materialization/serialization overshoot. If actual work exhausts/exceeds the allowance, stop before requesting another payload, preserve diagnostics, and return incomplete. H3/P3 must settle the byte-accounting repair; an oversized record cannot repeatedly be charged as only 1 MiB to justify further reads. Count/key operations also have bounded request counts and observed cost, never a zero-latency claim.

For coherence, explicitly permit the **fully fenced revision-barrier proof** below as an alternative to `spec:169`'s mandatory final reread of every source in one transaction. This is a contract amendment, not an assumption that the frozen wording already permits skipping those reads. Every selected witness is still read/validated/hashed in this preparation; the barrier proves those exact bytes and membership were unchanged across all its slices. Where all-writer fencing is unavailable, retain and charge coherent source **and ordered-range** revalidation. If that cannot fit, abstain. A witness-only reread cannot repair unseen-insert races.

### R3 — High: automatic-practice delivery and truthful provenance remain required completion work

**Evidence:** `spec:9,117,123–139`; config `releaseScope.automaticCoachingEnabled=false`; r1 `amendment-r1.md:29–31`. This config cannot satisfy an automatic-personalization acceptance test. Summary-only staging may be useful sequencing, but root explicitly retains Owen's original objective. A later enablement identity, connected selector, actual-Claude integration and finite exhaustion adapter remain on the implementation DAG.

App `engine.ts:164,201–203` wraps prompt queues modulo length; the real-engine probe consumes the exact 501-character `he` plan and reaches its first prompt again at 513 synthetic milliseconds. The existing strict result validator still accepts that run. Thus schema validity does not enforce finite certificate delivery. This is a feasibility counterexample, not a human speed claim. No automatic pilot should inherit modulo repetition after the certificate boundary without a new reviewed certificate rule.

App `profile.ts:10–16,57–85` and `storage.ts:87–93` define `practiceFocus` as the old baseline selector's evidence/score. New coach metadata cannot be placed there truthfully; coercing its source to `baseline` passes shape validation while falsifying its meaning. `manualDrill` must also remain manual. **Amendment:** carry the new policy decision and certified plan in a separate immutable in-memory coach snapshot; run ordinary practice prompts without spoofing those legacy fields. Persist a separate versioned historical decision only if reloadable explanation is required. Freeze a separately reviewed enablement config after C2/root acceptance.

The smallest finite-delivery adapter should stop admitting further practice text after the last certified prompt, with exact timing/result eligibility behavior settled jointly by the engine owner and actual Claude. It must neither silently early-complete a 30s result nor flag a safety stop and then count it as an ordinary completion. A bounded continuation is possible only if its complete ordered content is independently certified and frozen before admission; runtime recertification/rotation is not needed for the first pilot. Engine tests and actual-Claude flow acceptance choose the concrete boundary behavior; this report does not choose UI or introduce a new metric meaning.

### R4 — Medium: freeze component status and validator interfaces before parallel implementation

**Evidence:** `spec:47–55,155,179–196`; sidecar schema `$defs.time` at `23–26`; checker `check-contract.mjs:38–73`. The proposed `BaselineStatus` sketches multiple independent proofs, then adds summary and nullable coaching completeness in prose. It can represent truthful outcomes only if those component distinctions survive the implementation. A single top-level pending/complete flag is insufficient: capped participation can be proved while summary ordering or coach selection remains incomplete.

The schema uses `format=date-time` and `pattern=Z$`, while the custom oracle additionally enforces canonical millisecond UTC and round-trip date validity. A conventional validator's date-time acceptance can therefore be broader than this checker; format assertion itself also depends on validator behavior. The [JSON Schema 2020-12 format contract](https://json-schema.org/draft/2020-12/json-schema-validation#section-7) distinguishes annotation from assertion and defines date-time through RFC 3339. The probe executes the frozen checker, confirms all 148 checks, and demonstrates its rejection of a no-millisecond UTC string even though the declared pattern permits it. No standard schema validator was installed or claimed. Metadata's strict shape is still only prose (`65`), not an implemented validator/schema.

**Amendment:** freeze a typed component status/proof union with semantic validators and negative fixtures before writers/UI integrate. Tighten machine timestamp constraints to the canonical 24-character form and keep calendar round-trip validation. Add the metadata validator and partition-origin rule to the amended contract. Do not infer transactional, model-loading or application authority from passing the custom schema checker. Decision sidecars are optional in the minimal first implementation; before adding them, specify source-hash bindings sufficient for historical explanation rather than relying only on source IDs and the destination result hash (`spec:144–159`).

## One minimal storage/lifecycle protocol for reconciliation

This is the recommendation for a small safe implementation; no part is implemented by this report. Changes to the frozen contract are explicit in R1–R4.

1. **Atomic upgrade/bootstrap and writer fence.** Upgrade `typeforge` from version 2 to 3, preserving the existing `results` store/index unchanged as legacy, and add `currentResults` with the same raw `(completedAt,id)` index, `coachMembership`, and one `coachMetadata` record. Generate one default opaque context, active/legacy epoch, canonical cutoff and safe integer revision in the upgrade transaction. No lifetime traversal, source rewrite or copy is needed. A fresh DB gets an empty legacy partition. Only the actual pre-v3 upgrade path may bootstrap; missing/malformed metadata afterward is unavailable, not permission to bootstrap again. Validate upgrade abort/retry and metadata atomicity in a real browser.
2. **Capture without blocking General.** A run captures `(contextId,epochId,purpose)` before typing when context authority is ready. General/manual starts immediately even when it is unavailable; an uncaptured run may save as an ordinary current-partition result, but cannot later be assigned an epoch by guessing. Optional baseline/pilot entry must know whether capture succeeded. Context membership is separate from coach availability: invalid/missing coach config never changes assessment semantics or disables General. Never hold the native editor waiting for optional history.
3. **One save boundary, including retries.** Validate and clone the result and compute canonical hash before opening a write transaction. In one `readwrite` transaction scoped to both source partitions, membership and metadata: check the ID in both source stores, add a new source only to current, add captured membership when available, and advance the durable revision. Captured old-epoch membership remains old even if reset occurred before save completion. With valid metadata but no capture, source save plus revision is allowed without membership, and is deliberately excluded from coaching. With missing/corrupt metadata, ordinary current source recovery must not silently recreate policy authority; any repair path must keep policy unavailable until separately established. A source ID conflict cannot overwrite an existing payload or recapture its epoch. Resolve only on transaction completion, not on request success.
4. **Preserve unsaved recovery.** Existing `app.ts:310–312,544–570` and `unsaved.ts:17–24,57–92` retry result-only payloads and reconcile failures by ID existence. The app integration owner must retain the immutable capture token alongside the existing in-memory `SaveRecord` (or an equivalent session-local ID map) so retry cannot capture the current epoch. Distinguish source-saved from policy-membership-ready; a same-ID source lookup alone is not proof of membership/hash equality. Reconcile identical retries against both stores and exact bytes; conflicting bytes fail integrity. Failed/blocked saves retain existing export/retry/recovery behavior. Reload cannot recreate a lost capture; it remains unknown.
5. **Reset and source deletion.** Reset replaces only active epoch and advances revision in one metadata transaction. Do not retag source rows or delete assessment history; old in-flight saves stay old. Delete a source from its actual partition and its membership in one transaction that also advances revision. A cross-store duplicate/conflict is diagnostic; do not silently choose one as policy evidence. Membership deletion/repair and any later import/source rewrite must also participate in revision/atomicity. Source existence remains authoritative: an orphan sidecar never resurrects a result. Deleting a current membership cannot turn that source into legacy. Metadata repair, revision overflow and DB recreation require explicit unavailable/recovery handling; no reset-to-zero ABA counter.
6. **Deterministic merged source API.** P3 needs a bounded storage revision/adapter; its unmodified one-store API is insufficient. Merge reverse raw compound keys from both indexes using IndexedDB key comparison, not locale sorting or JSON-converted cursors. Use a versioned in-memory/structured-clone cursor containing both last-examined raw keys and exhausted flags; retain each store's key-only lookahead without skipping payloads. Equal timestamps use exact ID ordering. Both streams, invalid/incompatible rows and side lookups share the same ledger and cooperative slice caps. Cross-store ID uniqueness is checked by all source writers; a policy lookup must detect any observed dual-store conflict, never double count. Preserve excluded/unindexable diagnostics per partition. `getResult`, history pagination, existing calibration, deletion and explicit export all see the logical union; export emits valid readable source results once, no metadata or new copied private text. Do not leave old history/calibration stranded in the legacy partition. Explicit export remains a separate user action, not an automatic policy scan.
7. **Revision-barrier preparation.** Read and validate metadata `(authority identity,context,epoch,revision=r0)`; charge it. Perform budgeted source/membership reads across slices, validate/hashes, select witnesses/windows and derive the pure snapshot. All mutations affecting classification, range ordering or existence must atomically advance the same durable revision, including ordinary incompatible/uncaptured saves, deletes from either partition, membership change and reset. Old bundle writers are fenced by DB version; any recovery/import tool must use the same path. After asynchronous hashes/computation, open a final readonly transaction scoped to sources, memberships and metadata and recheck the complete authority identity/epoch/revision. Reject any mismatch, unreadable metadata, late generation, changed config or started run. This barrier substitutes for redundant final payload rereads only after explicit contract acceptance; it is sound because every relevant intervening write changes the checked revision. If any writer can bypass it, this proof is unavailable and the bounded coherent source/range fallback is mandatory. Scope/reset identity prevents revision reuse from looking unchanged.
8. **Admission, invalidation and as-of time.** Linearize the snapshot at final coherent admission, not at eventual UI render or notification delivery. Capture wall-clock `now` once; keep exact inclusive 30-day arithmetic and monotonic run timing. Source writes after that point affect a subsequent preparation; this is not a promise of latest data at the physical first keystroke. Before publishing, check local preparation generation/context/config and pre-insertion state again. Freeze active text/settings/predictions/evidence; never retrofit late reads or deletion into a running result. Broadcast a small invalidation after committed changes, with a storage-event fallback where needed; receivers invalidate pending/idle preparations and reread durable authority rather than incrementing a private counter as proof. On focus/pageshow/BFCache recovery always revalidate or discard cached preparation, even if no message arrived. Cancellation saves work; generation/revision checks establish correctness. No listener may steal focus or rewrite active input.
9. **Blocked upgrades and downgrade behavior.** Existing code uses `onversionchange` to close its connections, but a nonclosing connection can still block v3. While blocked, optional policy is unavailable and General remains usable. Handle late open success after a blocked/aborted request without leaking a connection or duplicate bootstrap. Once v3 commits, an old v2 bundle's next explicit v2 open fails `VersionError`; do not claim downgrade compatibility or create a replacement empty DB. Old running pages may finish in memory and use established export/recovery behavior; users must return to the new build for database access. New code must read/export old schema-v1 results from both partitions. This explicit compatibility tradeoff is part of root acceptance, not an undisclosed consequence.

The transaction facts above follow the [W3C IndexedDB specification](https://www.w3.org/TR/IndexedDB/#transaction-lifecycle), [transaction scheduling](https://www.w3.org/TR/IndexedDB/#transaction-scheduling), and [open algorithm](https://www.w3.org/TR/IndexedDB/#opening). Overlapping transaction scopes control write ordering; requests cannot be queued arbitrarily after a transaction becomes inactive. Database open with a lower version fails, and open connections can block an upgrade. Use transaction completion for success; compute asynchronous hashes outside live transactions. These are specification requirements, not browser acceptance evidence for the proposed implementation.

## Bounded selection proofs and truthful outputs

**One preparation, one ledger.** Reserve companion reads and the final proof before exhausting the source allowance. A 25-source slice followed by 25 memberships is not one 25-row policy slice. Use smaller source slices, charge all companion reads, then yield after at most the reviewed cooperative work. A cached ID/hash is only a hint: actual point reads in a new preparation are charged. Reusing a validated value already read under the same proven revision can avoid another physical read; issuing the request again always costs again. A final metadata barrier must itself fit. Bounded restarts after revision changes require a fresh explicit request or consume the same remaining automatic allowance; do not retry forever under new budgets.

**Capped participation:** ten unique present, compatible, valid sources/memberships under coherent authority prove `counted=10` and cap completion. They do not prove lifetime total ten, newest summary selection, or a complete coach window. With fewer than ten, report an exact count only after the applicable complete candidate range is exhausted; otherwise it is a lower bound and incomplete. No age expiry applies to participation. At 0/1/9/10/11 valid sources, capped values are 0/1/9/10/10; ordinary errorful one-insertion completions can count, but empty/interrupted/unsaved results cannot. No sticky unlock.

**Newest-ten summary:** traverse the merged order and examine/classify every potentially newer source until ten qualifying assessments have been selected, or exhaust the candidate range. Use one coherent revision for all pieces. Ten old cached IDs alone cannot authorize a current median; an eleventh newer source can replace one without changing any old witness. Pending/failed eleventh saves are absent and leave the previous valid selection intact. Practice never replaces summary assessments. Fewer than ten means no ten-source median. Null accuracy in any selected source leaves accuracy null with its valid-source count; WPM may remain available. The output includes the selected IDs/hashes/range/proof identity, not a claimed exact lifetime total.

**Newest20/30-day coach:** traverse newest-first, validate the canonical time/settings/quality/purpose/membership of each candidate before selecting sources, and keep the captured `now` fixed. Stop successfully after the twentieth qualifying in-window completed run only if every newer candidate was examined, or after the entire in-window range is exhausted with fewer than twenty. Exactly `now-30d` is included; only strictly older valid time proves crossing the time boundary. Skip future sources with diagnostics. Corrupt mixed-type index keys cannot themselves prove a chronological boundary; retain their native cursor identity and validate before using a time cutoff. Unindexable invalid rows remain excluded with diagnostics. Errorful/no-clean runs that meet source admission consume slots; clean sentence selection comes later. A byte/row/time/abort/failure stop before the proof is incomplete, never no-effect. Do not use a context/epoch boundary as an index-range stop unless an actual proven index supports that boundary; the raw history index has no such grouping.

**Revision consequence:** all selected reads may span slices only with the final all-writer revision proof. Witness point rereads with an unchanged local counter do not detect an uninstrumented newer insert. Our probe executes P1's own relation and shows it accepts such an insert when the revision input stays unchanged. This is expected evidence of the relation's limit, not a claim that P1 already implemented a faulty transaction.
