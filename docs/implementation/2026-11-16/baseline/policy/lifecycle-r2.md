18 November 2026. P1 r2 adopts A2 `6418bcc` as contract direction and accepted P3 source `3e31425` / evidence `5161dba`, H3 approval `884dbec`, root integration `29d58f4`. This is a proposed consumer contract, not approval to migrate a real database. ## Atomic physical origin and save lifecycle

Upgrade database `typeforge` v2 to v3 in one versionchange transaction: preserve `results` and its `completedAt-id` index unchanged as **legacy**, add `currentResults` with the same key/index, `coachMembership` keyed by result ID, and `coachMetadata` keyed by the fixed out-of-line key `authority`. Insert exactly one strict metadata value during that transaction. Fresh databases have an empty legacy store. Generate `databaseId`, default context, initial active/legacy epoch, cutoff and revision zero once per actual upgrade attempt; an aborted upgrade leaves none of them committed. There is no lifetime enumeration, source payload copy or rewrite. Only this upgrade creates authority. Missing metadata after committed v3 is unavailable, never a new bootstrap.

`metadata-membership.schema.json` is the machine shape and `interfaces-r2.ts` the typed seam. Metadata IDs are opaque nonempty strings <=128; database identity is fresh across actual database recreation. `sourceRevision` is a nonnegative safe integer. UTC must match the explicit canonical machine pattern and pass calendar round trip. Initial legacy admission requires **physical legacy origin**, default context, active epoch equal to `legacyEpochId`, `completedAt<=legacyCutoffCompletedAt`, ordinary historical purpose assumption and normal exact result compatibility. This is disclosed same-local-context historical evidence; no device identity is inferred. Current sources require a matching membership and can never become legacy through a missing membership, delayed save or clock rollback. A current ID equal to a legacy ID cannot create a second source.

Capture `(databaseId,contextId,epochId,capturedAt,purpose)` before first insertion when authority is ready; retain it with the source through Again, navigation and retry in session memory. General/manual remain ready without capture. An uncaptured run saves to current without membership and stays outside policy; config failure must not prevent capturing an ordinary assessment. A reload that loses capture cannot reconstruct it from time or current epoch. Membership stores the complete canonical source hash and source kind, not a hash of response text. Exact capture values bind retry; never recapture an old source into a new epoch.

Before a save transaction: clone/strict-validate the source and capture; compute the canonical complete source hash asynchronously. In one overlapping readwrite scope `[results,currentResults,coachMembership,coachMetadata]`, inspect both source IDs, reconcile identical retries, add a new source only to current, write captured membership when its database/context lineage is valid, and advance metadata revision. Captured old epochs remain old across reset. An identical source plus exact original membership is idempotent. If source exists but membership was deleted or differs, do not repair/recapture it silently: return `sourceSaved=true,membershipReady=false` and a diagnostic (or a source-integrity error on conflicting bytes). Same ID/different canonical source hash never overwrites. Identical legacy retry remains physically legacy, without newly assigning membership. Hashes needed for existing-source equality are computed outside the live transaction; re-read/check the corresponding stored value under the same all-writer revision/final transaction, or abstain rather than await hashing inside it. Resolve success on transaction completion, never request success. Abort cannot leave partial source/membership authority.

With missing/malformed metadata, ordinary current source recovery may commit without membership, but policy remains unavailable. Such a write cannot masquerade as fenced authority. Metadata is never silently repaired later. Revision overflow also disables optional authority: do not reset/wrap the counter; ordinary save/export remains possible, policy cannot resume until an explicit separately reviewed recovery establishes fresh lineage. Current contract defines no automatic metadata repair, rebootstrap or revision rollback. Database deletion/recreation is explicit destructive user work outside the pilot; new databaseId invalidates every old capture/preparation. If deletion is blocked, do not create a replacement database name.

Reset is one metadata transaction changing only active epoch and revision. Deletion scopes both partitions, membership and metadata; remove the actual source and membership atomically and advance revision. Missing-source deletion is idempotent; a membership removal that changes classification is still a revision mutation. Old sources/predictions remain on non-destructive reset. A cross-partition duplicate is integrity failure, not a choice of preferred payload. Orphan memberships never resurrect deleted sources. Missing current membership is excluded/diagnosed, not evidence of no history or legacy origin.

## One preparation ledger

One lookupId owns **25 examined row/point attempts / 4 MiB per cooperative slice, 500 / 16 MiB overall**, including sources in both stores, metadata, memberships, missing/failed point requests and final proof requests. Reuse already validated same-preparation values under one proven revision; issuing a physical request again costs again. Charge a row/operation attempt before requesting a point value even if missing, rejected or aborted. Source prefix measurements follow accepted P3 actual-work semantics: exact completed JSON bytes plus bounded examined prefixes, not whole-value serialization followed by capped charging. Reserve up to 1 MiB before a source/membership/metadata request; strict compact metadata/membership may use a smaller separately enforced ceiling (4 KiB). Apply the same prefix ceiling to corrupt companion values: never fully serialize an arbitrary corrupt metadata record to discover it is large. Reservation is capacity, not actual bytes. On settlement release unused capacity; charge the actual examined prefix even on structural failure. No payload retry under a new ledger.

Reserve companions and final proof **before** consuming the remaining allowance. The storage owner may use source batches smaller than 25 to leave membership/meta space; 25 source requests followed by 25 memberships are not one slice. Count requests: at most four per preparation (store+index for each partition). Key-only requests: at most 2 per examined source plus four boundary/lookahead requests, absolute 1004; stop incomplete rather than repeat key discovery without a cap. These operations do not materialize a source but their elapsed/native costs are observed, not zero. Yield after <=25 examined attempts, 4 MiB actual bytes or 8 ms cooperative processing; a single native operation/clone can overshoot and is reported. No absolute browser heap/I/O/latency cap is promised.

`record-limit` on an oversized/cyclic/unsupported/deep source **or companion** is a terminal incomplete stop for the whole automatic lookup, through every own partition/slice loop. It never implies range exhaustion/no target. Preserve excluded raw cursor/source, nullable `oversizedSerializedBytes` and explicit `oversizedByteLowerBound` (for oversize >=1 MiB+1; companion ceiling uses its actual bound). Unknown counts/totals stay null. Do not zero-coerce, run another partition after this stop, key-lookahead to fabricate exhaustion or automatically restart with fresh caps. Explicit continuation is a new user-requested bounded lookup after the retained raw cursor; it is not automatic completion of this policy snapshot. Independent capped participation already proved under final coherent authority can remain complete; any component depending on unfinished range remains pending.

## Conditional final authority and admission

Read/validate/hash metadata and all required sources/memberships within that ledger. Capture one `now`, generation and config identity. Hash source bytes outside live transactions. All proof methods must bind database/context/epoch/revision, exact canonical config, ordered selections and source hashes. **Alternative A, only with the complete shipped writer fence:** after computation, one final readonly transaction overlapping `[results,currentResults,coachMembership,coachMetadata]` rechecks full metadata identity/epoch/revision against the captured authority. The metadata point read itself is charged and reserved. No witness-payload reread is mandatory in this explicitly adopted revision-barrier alternative: every relevant intervening contracted write advances the same revision. A transaction resolving unchanged linearizes the snapshot; writes after it affect the next preparation. A local notification count or cached revision input is insufficient.

**Alternative B, when the fence is unavailable:** within the remaining same allowance, obtain a coherent ordered-range and all source/membership revalidation under overlapping transaction scopes, including every potentially newer candidate. Since hashes are asynchronous, compare the synchronously re-read validated data with the cloned canonical content already hashed outside, or compute and bind the complete revalidation result outside a closed transaction before an equally coherent final proof; do not pretend an inactive transaction spans arbitrary awaits. A witness-only reread misses unseen inserts. If this complete coherent proof cannot fit or be expressed, return pending/unavailable. No hidden second budget, no automatic fresh-cap retry.

Immediately before publishing/admitting: generation, epoch, config, database lineage and pre-insertion state must still match. Deep-clone/freeze the admitted snapshot, text and predictions before first accepted insertion. Nothing late changes an active run. On committed mutation, broadcast invalidation with storage-event fallback; on focus/pageshow/BFCache restoration, reread authority or discard preparation even without a message. New relevant local mutations invalidate idle/pending preparations. Notifications cannot steal focus. Source deletion during an active run affects subsequent preparation, leaving its historical in-memory snapshot intact.

Blocked upgrade, unavailable IndexedDB or late success leaves General/native input usable and preserves in-memory export/retry. Close late connections on cancelled/blocked attempts. After v3 commits, a v2 bundle's explicit v2 open fails `VersionError`; no downgrade support or replacement empty DB is promised. In-flight old pages can retain/export their result and retry on the new build. Historical schema1 result readability survives the database-version change.

A late failure remains recoverable without changing active run identity/text/focus; reload loses session pending captures and the next ordinal reuses the uncounted number.
