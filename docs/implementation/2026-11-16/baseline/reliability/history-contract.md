The original 92803c8 byte interpretation failed independent H3 review. This revision replaces capped charging after full serialization with bounded JSON-prefix traversal and a terminal incomplete `record-limit` state; independent delta acceptance remains pending. Original frozen receipts are preserved, not relabelled as passing evidence.

H1 owns storage.ts and new history retrieval tests. H2 owns this contract and lifecycle handoff. U1 is a separate report-only Orca helper owning undo-review.md; it cannot edit production or tests. ## Additive API

`readHistorySlice({ before?, rowLimit?, byteLimit?, signal?, compatible? })` returns valid `results`, opaque raw compound IndexedDB `cursor` (last examined value, including corrupt/incompatible values), `complete`, `reason`, `examinedRows`, `examinedBytes`, bounded diagnostics and operation-cost observations. `scanHistory(options)` joins slices with an event-loop yield between them, maximum 500 examined rows / 16 MiB automatically. A slice admits at most 25 examined values / 4 MiB. Optional smaller limits cannot exceed these hard caps. Compatibility is a pure synchronous predicate applied after strict v1 validation; excluded values consume budgets. No mutable derived store or dependency is added.

Order remains reverse `(completedAt,id)` index order. Raw IDB cursor keys are retained even for indexable invalid keys (non-date strings, numbers, dates, etc.); callers must preserve the opaque key unchanged. An exclusive upper bound resumes without repeating/skipping valid results. Key-only lookahead proves exhaustion at exact boundaries without examining another payload. Unindexable rows are counted by store/index counts and retained. All diagnostics are per-call, not the legacy mutable warning singleton. `complete` means the indexed traversal is exhausted, not that every stored record was valid; exclusions/unindexable counts stay explicit. Budget/time stops, abort and failure are incomplete; failures retain their message and already-examined cursor/results.

Raw cursors belong in memory or structured-clone storage, not arbitrary JSON/URL conversion: corrupt indexed Date/binary/array keys must preserve their native identity. `unindexableRows` is null until count requests succeed; unavailable counts are never fabricated as zero. Abort/failure envelopes are diagnostic partial work, not a ready policy snapshot; restart failed preparation rather than assuming that a predicate which threw classified its last examined row.

## Bytes, scheduling and unavoidable work

The persisted valid-record ceiling is 1 MiB. Before requesting a value the reader reserves this ceiling; if less remains, it stops without consuming that key. This conservatively underfills a byte budget by less than 1 MiB and avoids deferred/skipped valid records or repeated value probes. Exact limits are permitted. The bounded path never builds a whole-record JSON string or UTF-8 buffer. It traverses a JSON prefix, counts native JSON escaping and UTF-8 widths incrementally, and stops at the 1-MiB per-record prefix. Numeric tokens use finite number-to-string formatting (nonfinite JSON tokens are null and later fail strict shape validation). Full plain-JSON values within the ceiling have exact byte counts; invalid/incompatible values still consume their measured work allowance. A separate structural validator then checks the bounded value without serializing it again. Public legacy validation still uses its unchanged native JSON-size check.

`examinedBytes` is the sum of examined JSON-prefix byte allowances, <=4 MiB/slice and <=16 MiB/automatic lookup; valid and ordinary invalid JSON records have their full exact sizes counted. On oversized prefix cutoff it includes 1 MiB, **because actual traversal stops there**, not because a full larger serialization was silently discounted. One next scalar can be inspected to establish that its escaped UTF-8 token cannot fit; no oversized string/byte buffer is allocated. A cyclic/non-JSON/over-depth value charges its already-traversed prefix before stopping. Ancestor tracking is bounded to depth 32 (greater than the valid schema), and corrupt property names are not copied into a second `Object.keys` array by the measurer. Unsupported object types cannot pass strict result validation and are conservatively excluded rather than invoking native hooks or traversing arbitrary clone graphs.

An oversized, cyclic, unsupported or over-depth record returns **`complete:false, reason:'record-limit'`** immediately, with the excluded record's last-examined cursor. `scanHistory` carries this stop out of the whole automatic lookup; it does not yield and restart the exception in another slice. Consumers of `readHistorySlice` must also treat record-limit as terminal for their current automatic lookup. Explicit continuation is a new user-requested bounded lookup after that cursor; the following unexamined valid row stays untouched. No key-only lookahead is attempted after record-limit, so exhaustion is unknown until explicit continuation proves it. This conservatively affects automatic scans containing small cycles as well as very large corrupt values.

API delta for A2/future consumers: `HistoryRead.reason` adds `record-limit`; `diagnostics.oversizedSerializedBytes` becomes `number | null` (zero if no oversized exclusion, null when the exact total was deliberately not measured); `diagnostics.oversizedByteLowerBound` gives the known minimum (1 MiB + 1 for an excluded oversized record). Never coerce null into an exact total or retry record-limit automatically. Other cursor/count/exclusion meanings stay unchanged.

Native IndexedDB must still materialize one value before its size/shape is known. A single native oversized/unsupported materialization can exceed logical budgets and cannot be cancelled midway; record-limit prevents its repetition inside the automatic lookup. Browser-native count queries, raw key enumeration and string/clone representation also have browser-dependent costs. These guardrails bound avoidable JSON-prefix inspection/expansion and returned payload, not absolute native heap/I/O or wall-clock latency. No dual-partition/epoch architecture was implemented.

After 8 ms accumulated synchronous value-processing work, a slice ends before its next value; the automatic consumer yields before resumption. Each slice reports maximum single-operation duration and overshoot beyond 8 ms; timing values are observations, not a performance acceptance verdict. No controlled CPU traces are run in parallel lanes.

## H2 integration contract (separate root-assigned implementation)

General/manual render and accept input before optional reads. Maintain independent generation counters for preparation/page/summary; advance the relevant counter on navigation, restart, settings/context change and run start. Maintain a source data revision, incremented on successful local save/delete/reset and cross-tab invalidation; dispatch captures `(generation, revision, context/policy identity)`. A callback may publish only if all captured identities still match and the consumer is idle/pre-insertion. Correctness relies on identity checks even if abort fails. Abort old owned requests on supersession; blocked/rejected/delayed reads set optional unavailable/loading state while General remains ready. A run freezes its selected evidence before first accepted insertion; later callbacks/deletions never rewrite the active snapshot or historical predictions.

Cross-tab invalidation: a later integration owner must choose a minimal same-origin notification (e.g. BroadcastChannel with a storage-event fallback) after committed mutations; receiving tabs advance revision, invalidate pending/idle profiles and next preparation. On focus/pageshow also revalidate, since messages may be missed. This API spans separate readonly transactions and is not a multi-slice snapshot: concurrent mutations require discard/restart, not a claim of coherent exact totals. It does not itself implement notifications, revisions, caching or UI.

Incomplete profile scans abstain. Incomplete summary scans expose partial status and never exact lifetime totals. Visible pages replace rows, initially at most 25 and at most 100 mounted; cursor is last examined, not last valid. Explicit continuation starts another bounded scan with the retained cursor and same lifecycle guards; source revision changes reset traversal. Export remains a separate explicit valid-readable-only action; corrupt values stay in IndexedDB. Assessment preparation stays on the exact newest-ten-compatible-sentences path and separate cancellable/yielding lifecycle; neither new caps nor profile compatibility alter its meaning. Retest waits for exact resolved origin and compatibility. P1 decides policy/context/metric cohort identity before later integration. MetricVersion 2 remains deferred.

P1 coordination: policy lead accepted the existing budgets and proposed distinct capped baseline-count and newest-20-compatible-run/recent-window queries. `scanHistory.complete` remains full indexed exhaustion. A later consumer may use slices to prove its narrower cohort/window complete only under an explicit reviewed stopping rule and the same total lookup budgets; it must not reinterpret a budget stop as proof. P1's proposed legacy provenance/context sidecar remains a contract-only root review dependency; this API introduces no sidecar or new mutable source.
