## Bounds and limitations

The original code reserved 1 MiB before requesting a value but fully serialized/encoded oversized values and then capped their charge. H3 correctly rejected that control flow: 17 exact 2-MiB rows produced 8/32 MiB against 4/16-MiB limits. The corrected bounded path traverses at most a 1-MiB JSON prefix per record without whole-record JSON/UTF-8 allocation, charges prefixes even when cyclic/unsupported, and returns terminal incomplete `record-limit` so a native oversized/unsupported materialization cannot repeat automatically. Exact total oversized bytes are now unknown/null with an explicit lower bound; they are not measured through an unbounded second pass. Reservation underfill and raw cursors remain. See the revised `history-contract.md` and fresh `byte-repair` evidence; native clone/key/count costs and atomic-operation overshoot remain limitations, while avoidable whole-value serialization is no longer classified as unavoidable.

`complete` means **indexed traversal exhausted**, not that every stored row is valid or no unindexable row exists. Counts/exclusions remain explicit. Multi-slice reads use separate transactions, not a coherent database snapshot. The API itself implements no generation/data-revision ownership, cross-tab signaling, UI state, policy sidecar or profile persistence. No new result types or metric-generation acceptance were introduced.
